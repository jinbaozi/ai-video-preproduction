# GPT-Image-2 专属适配

目标明确为 `gpt-image-2`、固定快照 `gpt-image-2-2026-04-21` 或 ChatGPT Images 2.0 时完整读取。先识别实际使用界面和操作模式，再编写提示词；不要把 Image API 字段假设为 ChatGPT 或内置图像工具都能控制。能力快照核验日期：2026-08-20。本文件是 GPT-Image-2 现行能力和禁止字段的唯一规范源；模板、示例与测试只镜像这里的规则，发生漂移时以本文件和当前官方资料为准。

## 当前默认路径补充（2026-09-08）

ChatGPT 非 API 任务以 [ChatGPT 清晰度与编排](chatgpt-astra-workflow.md) 为准，不加载或输出下述 API 参数。第7节是旧 API 能力快照，使用前必须重新核验，不能用作当前聊天端上限。透明背景等易变能力在不同官方页面存在差异，不将旧禁止项永久化。只写提示词时无需查询无关 API 能力。

## 1. 证据优先级与界面路由

若官方资料互相矛盾，按以下顺序裁决：当前 Image API 指南／对应端点 API 请求参数参考或 schema → 模型页 → 官方 Cookbook 的通用原则 → Cookbook 单个代码示例 → 社区经验。已知冲突：部分 Cookbook 编辑示例仍传 `input_fidelity="high"`，但当前 API 指南明确要求 `gpt-image-2` 省略该字段；Cookbook 一处写最长边 `< 3840px`，而当前 API 指南／生成参考明确列出 `3840x2160` 并采用 `<= 3840px`。部分通用响应对象或联合类型仍只枚举旧固定尺寸，但当前 Python／CLI edits 请求参数明确说明 `gpt-image-2` 支持合法 `WIDTHxHEIGHT`；判断请求能力时采用模型专属请求参数说明，并在下载后核验实际像素。

| 使用界面 | 适合任务 | 提示与参数处理 |
| --- | --- | --- |
| ChatGPT Images／内置图像工具 | 自然语言生成、上传参考图、交互式修改 | 输出自然语言提示与附件角色；只有界面明确暴露某项控制时才给参数。不要承诺 API 尺寸、质量或遮罩字段会被该界面执行。 |
| Image API | 单次新生成或单次编辑 | 新图用 generations，已有图用 edits；把 `size`、`quality`、格式等放在独立参数区。 |
| Responses API 图像工具 | 对话式、多轮生成与编辑 | 使用明确动词“生成／绘制”或“编辑”；可用 `action` 控制 generate／edit／auto。主模型可能自动改写提示，可从 `revised_prompt` 检查实际改写。 |

若用户只说“GPT-Image-2”但未说明界面，提示词本体仍可完成；仅在需要精确参数、遮罩或多轮 API 行为时追问界面。

用户指定 `gpt-image-2` 时保持该名称；不得为了“生产一致性”静默替换为 `gpt-image-2-2026-04-21`。只有用户明确要求固定版本并接受不自动跟随别名更新时，才把当前可用快照作为参数选项。

## 2. 任务模式与资产路由

先做两层判断：操作模式与交付物类型。通用分类细节见 [任务路由与结构化视觉](task-routing-and-layout.md)。

| 模式 | GPT-Image-2 提示策略 |
| --- | --- |
| 文生图 | 直接描述新画面的用途、场景、主体、关键细节、构图与约束。 |
| 参考图引导的新图 | 逐图定义身份／产品／风格／构图等角色，明确迁移到一个全新画面；不要误写成“只改图 1”。 |
| 整体编辑 | 指定图 1 为基图，列出允许改动、不变量和全局融合要求。 |
| 遮罩／局部修补 | 把遮罩视为提示驱动的区域指引，仍需写唯一改动、边界内外不变量和接缝要求。 |
| 多图合成 | 写明元素来自哪张图、放入哪张图或新画面的哪个位置，以及尺度、透视、遮挡、光色、材质、接触和阴影。 |
| 连续修订 | 使用最小 Prompt Delta；只改当前主失败并重述关键不变量。 |

交付物可为写实照片／人物、产品／电商、插画／概念图、海报／社媒、信息图／图解、UI／网页模型或多面板叙事。对结构化资产，组件数量、精确文字、阅读顺序和空间关系优先于氛围词。

## 3. 提示密度与稳定结构

### 简单任务

优先用 1—3 个清晰句子覆盖：用途与图片类型；场景、主体和唯一动作／表情；构图、光线与最重要限制。简单任务只保留当前场景最高风险的 2—4 组因果；输出前按完整句号和实际信息密度检查，超过 3 句或用分号绕成检查表时，合并同一因果链并删除次要细节。只写会改变可见结果的细节，不把摄影检查表全部展开。

```text
<用途与真实照片／插画类型>。<场景中的主体、动作、可见身份与造型锚点>。<景别构图、主光、综合色调、真实质感与少量必要限制>。
```

### 复杂任务

使用短标签和换行，保持以下稳定顺序；不需要伪装成 JSON，也不要用特殊权重语法：

```text
任务与用途：...
场景与背景：...
主体与动作：...
关键细节：<人物／产品／界面／图表中会改变结果的项目>。
构图与空间：...
光线、色彩与材质：...
精确文字：...（仅适用时）
约束与不变量：...
```

- 复杂场景先确定一个第一视觉主体，其余人物、道具与文字作为支持层级。
- 提示已具体时只规范结构和消除冲突；提示稀疏时才按视觉目的补充必要细节。
- 画幅既可用“竖向海报、左侧留文案区”等构图语言表达，也可在 API 参数区给出合法尺寸；不要把像素值混进摄影描述。
- 不因社区提示词常见就添加“杰作、8K、超高质量、RAW、获奖”等无任务依据的词。

## 4. 通用生成与人像专项

- 用“照片、插画、3D 产品图、海报、信息图、移动端 UI 模型”等直接声明媒介和交付物；加入实际用途，以帮助模型选择版式与完成度。
- 产品图先锁定几何、部件、朝向、标签、固有色和材质，再加入场景与氛围；不让装饰改变产品结构。
- 插画先写线条／笔触、形状语言、空间处理和色块关系；不要用“某在世艺术家风格”代替可观察特征。
- 信息图、UI、海报和多面板任务完整执行第 6 节的结构与文字合同。

### 人像专项

- 需要真实照片时直接写“写实照片／photorealistic photograph”，再用镜头距离、景别、机位、主光和真实纹理支撑；不要仅靠“高级感”。
- 自然抓拍要写成现实中可捕捉的一个瞬间：动作触发、唯一视线、眼周和嘴角变化、肩颈与手部受力。为保持纪实感，避免同时加入完美棚拍、奢华修饰和海报式戏剧光。
- 按景别、年龄、材质状态和用户意图选择可见纹理：近景可保留适龄毛孔、细纹或发丝，衣料磨损只在服装状态或叙事需要时加入；不要用纹理清单无端加龄、做旧或降低商业画面的整洁度。只在会破坏任务时追加“不过度磨皮／不做美颜滤镜”等少量限制。
- 详细相机参数只作为外观意图，模型会宽松解释。每张图保留一个景别、一个主机位、一个焦段意图、一个主光方案和一个对焦重点。
- 人物外观仍按 [人物外观、造型与表情](character-appearance.md) 分成身份锚点、造型变量和瞬时状态；当前景别不可见的细节不要写入提示词。
- 近景人像、真实人物身份保持、深肤色精确曝光、眼镜反光、复杂卷发边缘或年龄纹理是高风险项，应在约束中只锁定相应的可见验收点。

### 自然观看现实感

OpenAI 的“自然写实”范式是像描述一次真实抓拍：明确真实照片、现实中可捕捉的动作、景别／视点、自然光色、真实纹理和少量不完美，并避免重度修饰与舞台化。不要把它扩写成固定的“人眼焦距／光圈／动态范围”。需要具体规则时完整读取 [自然观看现实感](natural-viewing-realism.md)。

- 先写观察／相机位置、主体尺度、主要注意目标和一个可解释的清晰区，再写焦段线索。离焦程度须随物体相对焦平面的位置连续变化；同深度物体不能因为语义重要性而突然更锐，也不要写成“离相机越远越糊”。
- 人物看手机、书或近处产品时，写出同一个物理注视点、与距离相称的轻微双眼会聚、眼睑和头颈关系；手部写清握点、合理遮挡、指腹压力和接触阴影，避免笼统的“看向手机”。
- 屏幕或反光材质出现时，先让功能面朝向实际使用者，再把内容、表面和环境关系分开：平面透视、与涂层相称的反射／扩散响应、屏幕亮度、遮挡、噪声／颗粒和环境光必须属于同一照片。若既要表情又要屏幕可读，优先使用人物肩侧／过肩三分之四机位并保留屏幕透视缩短；不要把正面人脸和完整屏幕同时伪造成正对镜头。若精确 UI 重要，优先将合法截图作为内容参考。
- 生活方式照片保留少量使用痕迹与不完全对称，让道具服务人物活动；避免每件物品都完整朝向镜头、颜色完美配套或承担相同视觉权重。
- 混合光先确定主光和肤色曝光锚，再保留有动机的局部冷暖；不用“人眼 HDR”同时提亮窗外、室内和阴影。

## 5. 编辑、参考图与连续性

### 参考图角色与“生成／编辑”分界

按顺序给辅助参考图分配单一主角色：`图 2：服装`、`图 3：视觉特征`。待编辑基图可同时承载人物身份、产品几何、姿态、构图、背景与光线等一组显式不变量；“单一主角色”不等于把基图拆成互斥职责。小而职责清楚的参考集通常更易管理；不得只写“融合附件”。参考图只提供方向且用户要求全新构图时，写成“参考图引导的新图”，不要错误承诺基图像素级保留。

多图合成必须说明：从哪张图取哪个元素；放进哪张图的什么位置；如何匹配比例、透视、光线、色温、遮挡、接触与阴影；哪些内容完全不变。使用“编辑图 1，把图 2 的……放到……”替代含糊的“合并两图”。

### 编辑合同

```text
编辑操作：<唯一主要改动>。
参考图角色：<图 1...；图 2...>。
只允许改变：<明确区域、对象或属性>。
必须保持不变：<身份、脸型与五官、年龄、肤色、发型、表情、身体比例、姿态、构图、机位、背景、光线、文字等实际关键项>。
融合要求：<材质、褶皱、遮挡、尺度、透视、色温、接触与阴影>。
```

不变量只列任务真正需要保持的内容；不要把互不相关的几十项全部冻结。Image API 遮罩使用带 alpha 的 PNG，须与第一张输入图尺寸相同；完全透明区域表示可编辑区域，非透明区域表示保留区域。遮罩只是提示驱动的区域指引，不是像素级硬边界；多图编辑时遮罩作用于第一张输入图。输出具体文件大小限制前按当前 edits 请求参数重新核验。

### 系列人物与多轮修订

- 先生成并验收一张角色锚点图，再把已通过的图作为后续 edits／多轮上下文输入；不要只靠每次独立文本重建同一人物。
- 每张后续图重复最少必要的身份锚点与固定造型，主动改变 1—2 个轴。
- 用户只要求一个问题时采用单变量修订，并重述必须保持不变的身份、构图、背景、光线或文字；用户明确要求多个兼容改动时完整列入同一局部编辑合同。只有身份漂移风险或因果依赖明显时才建议分轮，不得静默删减用户要求。不要为“改暖一点”重新生成整份大提示词。
- GPT-Image-2 能提高身份与角色一致性，但不能保证跨图零漂移；关键系列需逐张人工复核。

## 6. 图中文字与结构化版式

把文字作为版式对象，而不是普通场景细节：

```text
只出现以下文字，逐字呈现一次，不得增删或改写："<精确文案>"。
字体：<类别、粗细>；颜色：<颜色与对比>；位置：<区域与对齐>；层级：<与人物／产品的关系>。
除以上文案外不出现其他文字、标志或水印。
```

- 文案尽量短；少见拼写或品牌词可在不改变最终文案的前提下补充逐字母拼写说明。
- 小字、密集标签、多字体或文字关键交付优先比较 `medium` 与 `high`，并把逐字一致、仅出现一次、不裁切、不重叠和无额外文字设为硬验收门。
- 文字能力已提升但仍可能拼错或错位；关键发布资产的质量检查必须明确写“先用 OCR 提取，再人工逐字核对”，然后按需用设计工具精修，不承诺一次生成即可交付。只写“检查文字”不满足发布门。

### 信息图、UI、海报与多面板

- 先声明交付物类型，再列必需组件、组件数量、层级、位置和阅读顺序；组件和精确文字作为通过／失败硬门。
- 信息图写清节点／步骤数量、连接方向、图例与标签归属；UI 写清屏幕类型、必需区块、当前状态、主操作和真实控件可供性；多面板写清面板数、网格、每格事件和跨格连续性。
- 要求“除指定文案外无其他文字、占位符、乱码、二维码或水印”，但不要生成独立 `negative_prompt` 字段。
- 验收顺序为：交付类型 → 必需组件／数量 → 精确文字 → 布局层级 → 风格／品牌适配 → 视觉质量。不能用平均分覆盖硬门失败。

## 7. 4K、参数与禁止项

用户明确采用 API 且要求 4K、原生像素或自定义尺寸时，完整读取 [GPT-Image-2 4K 与尺寸校验](gpt-image-2-4k.md) 并运行 `python3 scripts/validate_gpt_image_2_size.py <WIDTHxHEIGHT>`。分别确认尺寸是否合法、是否实验性、当前具体端点是否暴露该值。主提示词不加入“4K／8K”魔法词；像素只放参数区。

以下只适用于当前官方 Image API／明确暴露等价字段的界面：

| 项目 | 当前规则 |
| --- | --- |
| `quality` | `auto`、`low`、`medium`、`high`；`low` 用于草稿和快速试验，近景人像、身份敏感编辑、精确文字、高分辨率成品比较 `medium`／`high`。 |
| `size` | Image API generations／edits 可用 `auto` 或合法 `WIDTHxHEIGHT`；两边均为 16 的倍数，长短边比不超过 3:1，总像素 655,360—8,294,400，最长边不超过 3840px。总像素数严格大于 3,686,400（2560×1440）的输出视为实验性。Responses 工具按当前 schema，ChatGPT 界面不承诺精确像素控制。 |
| 常用尺寸 | `1024x1024`、`1536x1024`、`1024x1536`、`2048x2048`、`2048x1152`、`3840x2160`、`2160x3840`。 |
| 输出 | `png`、`jpeg`、`webp`；压缩 0—100 仅用于 JPEG／WebP。Image API 返回 Base64 编码图像数据，不支持 DALL·E 的 `response_format="url"`；需要 URL 时由应用保存并上传文件。 |
| 背景 | 仅 `auto`／`opaque`；当前不支持 `transparent`。需要透明资产时先生成纯色不透明背景，再经下游抠图，并提示发丝、玻璃、烟雾等复杂边缘需人工检查。 |
| 多结果／流式 | `n` 为 1—10；`partial_images` 为 0—3。只有用户需要相应工作流时才列出。 |

对 `gpt-image-2` 禁止输出：`input_fidelity`、`negative_prompt`、`style=vivid/natural`、seed、CFG、steps、采样器、`--ar`、`--no`、`response_format="url"` 或 `background="transparent"`。排除项写进主提示词的“约束与不变量”，保持短而任务相关。

- `quality` 是速度、成本与细节的工作流选择，不是“成片必然更好”的保证。最终任务可用同一代表性提示比较 `medium`／`high`，按身份、表情、文字和材质硬门选择。
- 用户强调低延迟时，当前官方指南支持推荐 `quality: low`，并说明方形通常生成更快、JPEG 比 PNG 更快；只有版式允许方形且不需要透明通道时才采用，不要为追求速度破坏最终画幅或交付格式。能力变化后须重新核验，不得把“通常更快”写成绝对保证。
- Responses API 只说明“选择当前支持图像生成工具的主模型”；要给出具体主模型名或代码时，必须在本次任务中按官方 Responses 指南核验，不能把 `gpt-image-2` 填入主模型字段，也不能沿用过期示例模型。

## 8. 定向修订与验收

| 失败 | 单变量修订方向 | 必须保持 |
| --- | --- | --- |
| 皮肤像塑料 | 仅恢复毛孔、细纹、绒毛、自然不对称和高光滚降，降低美颜磨皮 | 身份、年龄、表情、构图、光线方向 |
| 身份漂移 | 仅恢复参考图中的脸型、五官比例、肤色底调、眼眉、发际和年龄特征 | 已通过的服装／场景改动、姿态和机位 |
| 深肤色发灰或过橙 | 仅校正中性白平衡、宽柔补光和高光保留 | 固有肤色、五官、环境色和构图 |
| 眼镜遮眼或反光 | 仅调整灯位和柔光入射，使双眼可读、镜片无强几何反射 | 镜框、脸型、表情和背景 |
