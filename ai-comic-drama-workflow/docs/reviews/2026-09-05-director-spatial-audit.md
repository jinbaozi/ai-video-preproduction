# AI 漫剧工作流：导演与三维空间能力体检及优化方案

审查日期：2026-09-05。审查对象：本仓库 `0.2.0`，Git HEAD `5a04752`。

本轮范围：读取两份用户附件，核查当前源码、Schema、阶段资源和测试，执行只读诊断与隔离反例，检索公开资料，提出方案。未修改运行逻辑，未安装 Blender，未接入或调用付费生成服务，未创建新版本或推送 Git。

证据标识：**实测**表示本轮运行复现；**代码检查**表示由当前实现直接判断；**外部资料**表示来源实际支持的内容；**建议**表示尚待实现和验收的设计。建议不能理解为现有能力。

## 1. 总结：保留工作流骨架，补上真正的导演—空间—画面闭环

当前项目有值得保留的基础：13 个独立阶段目录、Canonical JSON、选择与人工批准、依赖失效、阶段化上下文、来源哈希和确定性交付包。

但它目前更接近“有时空字段的提示词工作流”，还不是具备充分证据的三维导演系统：

- 故事板主体是结构化时间轨道、文字及 SVG 示意；SVG 不是三维相机渲染。
- 已有图片分支主要通过本地测试素材复制验证流程，并未接通真实在线图片生成服务。
- 相机与场景字段不足以保证构图、遮挡、视线、动作接触在实际画面中成立。
- 部分表演信息没有进入执行提示词；最终审核、返修续跑和批量提交还存在已复现的可靠性缺口。

**推荐目标：把导演意图变成可计算、可观看、可检查的镜头，再选择生成方式，而不是继续增加形容词和提示词长度。**

建议的核心链路：

```text
原始资料 → 剧情事实与导演意图 → 已批准资产 / 场景 / 表演与相机时间轨道
                                       ↓
                         场景构建与逐帧状态求值
                                       ↓
                     图片故事板 + 空间俯视图 + 动态预演
                                       ↓ 人工批准
                     ┌─────────────────┴────────────────┐
                 三维直接渲染                    可选 AI 生成 / 风格化
                     └─────────────────┬────────────────┘
                             计划—实际画面对照
                                       ↓
                              音画剪辑 → 最终验收
```

这与 OpenAI 的 Astra 建筑可视化案例中“编写 Blender 场景、预览、检查、修正、最终渲染”的做法一致；案例支持这一工作方式，不证明任意叙事镜头或人物表演都能一次成功。[OpenAI 原始案例](https://developers.openai.com/blog/architectural-visualization-with-astra)

### 2.3 质量状态应重新分层

现在的 `generated_verified` 至少部分仅表示图片可解码、尺寸有效；这不证明角色一致、构图正确或表演合格。视频全片解码也不证明对白同步和叙事连贯。

建议分别记录，不以单个“verified”掩盖边界：

1. 契约与引用检查。
2. 文件可读、参数及解码检查。
3. 几何与投影检查。
4. 画面、表演和连续性检查。
5. 当前修订的人工作品审核。

允许提示词包在其交付范围内合格；不能把该合格升级成图片、视频或成片合格。黑帧、冻结检测应可区分故障与经批准的静止镜头 / 黑场，报告区间和参数，而非简单一刀切。

## 3. 对附件与网络资料的核验结论

两份附件都适合提供方向，但其中的能力评级、产品示例和工程推论必须分开。

| 资料 / 说法 | 实际依据与边界 | 本项目采用方式 |
|---|---|---|
| Astra 编程 Blender、检查渲染 | OpenAI 原文确有场景编程、相机路径和预览返修案例；不是本项目的导演能力测评 | 用作规划—执行—检查架构依据；不承诺“一次生成”或电影级效果 |
| ARC Prize 的 Astra 实测 | 原文涉及交互任务和简洁状态表示；不是影视调度评测 | 借鉴外置状态记录，不以其分数作为导演或三维正确率 |
| H3 提示词规范 | 官方仓库对运镜类型、幅度、速度以及主体动作有具体说明 | 建立明确摄影语义，区分平移 / 摇镜、推轨 / 变焦，保留对白与说话人 |
| H3 Max Director 实时接口 | 文档描述文本更新、可选起始图片及接收音视频流；未提供三维坐标轨道或输入控制视频的对应字段 | 只能作为单独实验适配器，不宣称 Blender 轨迹能直接硬约束该接口 |
| H3 Director 的 memory | 文档中的记忆范围是先前分段提示词 | 不等同于角色骨骼、场景几何或世界状态记忆 |
| fal 白模到实拍文章 | 具体案例使用 Claude Fable + Blender MCP；包含构图偏移、多次候选和人工挑选 | 借鉴白模、关键帧、叠图检查、分层返修；不把案例误写成 Astra / 本项目已实测 |
| LTX-2.3 3DREAL | 接口明确接收 CG / 游戏视频，支持可选外观参考图片；当前模型卡还有 strong-v2 | 可试验真正的视频条件风格化；仍受输入规格、风格域与几何漂移限制 |
| 固定“每段只有一个动作和一种运镜” | 可减少复杂度，但不是通用导演规则 | 采用一个主导戏剧目标，允许必要的并行动作及有时码的复合运镜 |
| 固定角色“永远画面左侧 / 右侧” | 相机绕行后屏幕关系可能改变 | 世界站位是事实；画面左右由相机投影推导，不能混为一个坐标系 |
| 所有镜头首尾状态必须完全相同 | 连续动作需要交接，但省略、时间跳跃、新场景、蒙太奇有不同语义 | 定义连续 / 跳时 / 转场的交接方式及批准依据，既防瞬移也允许合法剪辑 |

## 4. 推荐技术路线与职责边界

### 4.1 三个主体，各做其擅长的事

| 主体 | 应负责 | 不应承担 |
|---|---|---|
| 导演 Agent，包括可选 Astra | 剧情理解、人物动机、调度、摄影方案、场景代码草稿、看图返修建议 | 仅凭文字断言几何正确；绕过 Kernel 提交事实；凭品牌宣称效果 |
| 本地运行时 + Blender | 严格时间与状态求值、场景构建、相机投影、碰撞 / 遮挡检查、图片与预演渲染 | 自动推翻已批准剧情；把任意外部模型结果当作事实 |
| 图片 / 视频生成提供方 | 根据已批准条件生成外观、动作与候选媒体 | 充当世界状态数据库；保证未在接口表达的几何轨迹 |

优先采用 **Blender 后台 Python 构建与渲染**。原因是它易于绑定输入哈希、保存工程、重新执行和检查结果。MCP 可作为后续交互桥接，不是三维能力本身，也不是第一版必需组件。Higgsfield 的官方说明同样区分 Blender 场景桥接与生成能力，接入它不应取代本项目的 Canonical 契约。[Higgsfield 插件说明](https://higgsfield.ai/blog/higgsfield-blender-plugin)

不建议首版同时接 Blender、Unreal、多个视频模型、实时生成和大型可视化编辑器。先用一种场景执行器做通可验证的单场景，之后再扩展适配器。

### 4.2 JSON 仍是事实源，三维工程是可重建产物

- 剧情、身份、空间关系、时间轨道、相机参数及批准都保留在 Canonical JSON。
- 网格、贴图、动作资源和参考图按稳定 ID、版本、权限及内容哈希登记；二进制内容不塞进 JSON。
- `.blend`、PNG、预演视频、拼版故事板总图和 HTML 浏览页均是派生产物；记录生成器版本及源哈希。
- 用户手动编辑 `.blend` 后，要把受支持的差异导入为草稿修改提案，批准后再更新 Canonical；未能解析的差异不能静默覆盖事实源。
- “可重建”不要求跨不同 GPU、Blender 版本的所有渲染 PNG 字节相同。结构化数据及提示词要求确定性；媒体固定环境和随机种子后检查参数与画面差异，并登记真实文件哈希。

### 4.3 模型及生产路线是用户选择，不是默认强绑定

| 路线 | 推荐用途 | 可控边界 | 启用条件 |
|---|---|---|---|
| A：三维预演 / 直接渲染 | 先验证站位、表演节奏、摄影和剪辑；空间精度要求高 | 执行已建模的几何和相机；精细表情取决于角色模型与绑定 | Blender 实际探测通过；缺少角色模型时明确使用代理体 |
| B：三维控制视频 → AI 风格化 | 保留运动构图、提升视觉外观的候选路线 | 有真实控制视频输入仍可能漂移，需要画面对照 | 适配器规格匹配，风格适配，经用户授权与费用确认 |
| C：故事板图片 → 批量视频 | 用户已有模型账号；平台只支持图 / 文参考 | 属于软控制，不能承诺厘米级轨迹或完全匹配相机 | 实际验证接口及参考图槽位；接受相应降级 |
| D：实时导演流 | 交互试拍、探索候选镜头 | 会话记忆、迟到和输出漂移需专门治理 | 独立实验开关、费用上限、停止机制和用户确认 |

LTX-2.3 3DREAL 可作为路线 B 的小样候选，因其公开接口确有控制视频输入；模型主要面向写实转换，不应被强制用于所有国漫、2D 或自定义风格。具体规格和变体必须在执行时重新读取。[接口](https://fal.ai/models/fal-ai/ltx-2.3-quality/render-to-real/api)、[模型卡](https://huggingface.co/fal/LTX-2.3-3DREAL-LoRA)

路线 D 后置：H3 Max Director 的分块时长、提示词版本、输出时间戳与项目镜头不是同一个概念。建议专门记录会话事件、实际输出片段、更新版本和中止原因；断流 / 迟到时停止或标记缺口，不把冻结帧包装成正常表演。[接口依据](https://fal.ai/models/minimax/h3-max/director/api)

## 5. 如何真正提高导演能力

导演能力不等于自动多给几个景别。需要明确“为什么拍、拍什么变化、观众此刻应该知道什么”，然后用画面检验。

### 5.1 从剧情到表演的可追踪链

建议在阶段 04—06 增加或强化：

1. **场景意图**：叙事目的、视点归属、观众已知 / 未知信息、情绪起点与终点。
2. **人物行动**：目标、障碍、策略变化和反应，转成可观察的动作，而不只写“很愤怒”。
3. **节拍与转折**：哪句话、哪次视线变化、哪个动作改变局势；转折必须对应源事实或明确的改编提案。
4. **摄影动机**：为什么现在切近景、为什么移动、什么时候应保持不动；避免把所有镜头做成无理由的运动。
5. **剪辑设计**：建立镜头、主观 / 客观视点、反应镜头、动作接续、必要插入镜头、声音提前或延后进入的意图。

调度应与构图、场景、道具和叙事共同设计，而不是编完动作后再套景别。这与专业制作博客对 blocking / staging 的说明相符；上述契约字段是本方案的工程归纳，不是引用来源的现成 Schema。[StudioBinder：Blocking and Staging](https://www.studiobinder.com/blog/blocking-and-staging-scenes/)

### 5.2 阶段内分工，避免一次加载所有专家

按需顺序调用：剧情导演 → 人物调度 → 摄影 → 连续性 → 独立看图复核。每次只加载一个角色与相应量表，仍只返回草稿 `AgentResult`。

不是为每个阶段增加无限多个 Agent。简单镜头只需要当前专家；复杂对峙、道具交接、轴线变化等高风险镜头才增开专项审查。评审建议不能自动变为用户批准。

### 5.3 导演质量量表与审核证据

| 维度 | 要回答的问题 | 验证证据 |
|---|---|---|
| 叙事清晰 | 观众能否理解谁在做什么、为何变化？ | 剧本节拍与实际镜头一一对应 |
| 表演可信 | 情绪有原因、行为有过程、反应有时间吗？ | 动作 / 表情关键帧、节奏预演、人工复核 |
| 摄影有意图 | 景别、机位、运动是否服务当前信息？ | 导演意图、候选画面对比、批准理由 |
| 空间可读 | 谁在哪里、看向谁、如何移动是否清楚？ | 俯视图、相机画面、投影和遮挡报告 |
| 剪辑连贯 | 动作、视线、道具和声音能接上吗？ | 头尾对照、完整预演、时间跳跃说明 |
| 可执行 | 输入条件能被选定执行器表达吗？ | 能力卡、字段覆盖、实际生成 / 渲染验证 |

180 度轴线应作为默认连续性检查，不是永远不可突破的禁令；刻意越轴应具有导演理由、过渡方式和批准记录。[Adobe：180-degree rule](https://www.adobe.com/creativecloud/video/discover/what-is-the-180-degree-rule.html)

“出色”的最终评价仍含审美判断。建立固定剧本样本，盲评旧版与新版的叙事、表演、构图和剪辑；保存评审人、版本和意见，不用模型自评分替代用户评价。

## 6. 三维空间与时间的核心改造

### 6.1 在现有契约上扩展，不另造一套世界状态

以下为拟议契约，不是现有文件名称承诺。优先扩展 SceneSpacePlan、ShotTimelineSpec、StoryboardPackage 与 PromptPackage；仅在责任确实独立时拆分新文件。

| 契约领域 | 必要内容 | 关键约束 |
|---|---|---|
| 导演意图 | 场景目标、节拍、POV、信息揭示、情绪变化、摄影理由 | 关联剧本来源，核心改编须批准 |
| 场景与实体 | 单位、轴向、世界 / 局部坐标变换、实体尺寸、层级、几何代理、固定物、区域与出入口 | 相同实体 ID 跨阶段一致；未知尺寸明确标记，不由单张图假装精确恢复 |
| 表演轨道 | 世界位置、身体 / 头部朝向、视线对象、姿势、动作阶段、互动对象、道具持有者、情绪及外显动作 | 隐身 / 画外不是不存在；可见性与世界状态分开 |
| 相机轨道 | 投影类型、位置、旋转、传感器、焦距 / 正交尺度、焦点、机位目标、关键帧与插值 | 朝向、焦距和目标不互相矛盾；摄影语义与物理轨道相符 |
| 时间与交接 | 项目帧率、镜头本地时间、片段及成片时间映射、连续 / 跳时 / 换场说明 | 用有理数帧时间作为执行基准；区间边界规则统一，音频另保留采样时间映射 |
| 求值快照 | 指定时刻的实体、相机、道具和可见状态及源哈希 | 从轨道确定性计算，不允许另一位 Agent 独立重写快照事实 |
| 图片故事板索引 | shot_id、时点、camera_id、图片哈希、生成模式、源修订、审核 | 实际渲染图、AI 图片、示意图、待生成提示词必须区别标记 |
| 观测报告 | 计划值、实际画面观测、置信度、偏差区间和修复层 | 观测不直接覆盖 Canonical；核心偏差需重新生成或批准改编 |

### 6.2 坐标、插值和投影

- 建议三维档统一使用米制、右手系、Z 向上；每个场景显式声明。现有标准化 2.5D 输入按场景边界变换，保留原始值，不直接裁剪。
- 区分世界、物体局部、骨骼、相机和屏幕坐标；把“画面左方”转换为某台相机下的约束，而不是全局世界坐标。
- 位置插值、旋转插值、保持和缓动均需显式。角色不能因为关键帧少而瞬移；禁止默认采用最近关键帧代替当前位置。
- 相机投影负责确定构图、屏幕方向和主体尺寸；几何检测负责可见性及遮挡。Blender 官方 `world_to_camera_view` 实现确实使用相机变换及投影参数提供相机视图坐标，可作为投影实现依据。[Blender 官方源码](https://raw.githubusercontent.com/blender/blender/main/scripts/modules/bpy_extras/object_utils.py)
- 人物之间、人物与场景、相机与墙体、手与道具分别设置碰撞 / 接触约束；代理几何不代表最终服装、发丝或手指碰撞已精确验证。
- 景深、焦距和传感器等参数需要成组定义。Epic 的 Cine Camera 文档也按物理摄影参数组织相机；可借鉴其参数划分，但首版不必接第二个引擎。[Epic 文档](https://dev.epicgames.com/documentation/en-us/unreal-engine/cinematic-cameras-in-unreal-engine)

### 6.3 图片故事板必须是第一等交付物

选择图片 / 三维路线后，阶段 09 不应以文字 JSON 已齐全作为结束条件，至少应交付：

- 每镜相机视角的关键时点 PNG；1—3 张是默认选点数量，不代表只检查这些时间点。
- 场景俯视图，叠加人物路线、朝向、道具和相机位置。
- 可读故事板总图，显示镜头 ID、时码、对白 / 动作提示及图片状态。
- 动态预演视频，用于观看动作速度、情绪停顿、运镜和剪辑衔接。
- 图片 / 视频对应的状态快照及审核报告。

快速动作、遮挡变化、道具交接等必须增加检查采样，必要时逐帧或连续碰撞检查。有限抽样无异常不能宣称整个连续轨迹无碰撞。是否增加展示给用户的故事板帧数，可独立于内部检查采样选择。

首版使用简单代理角色和几何体即可验证空间。Wonder Unit 的 Shot Generator 原始设计强调可调整人物姿势、相机和俯视布局，适合作为轻量预演交互的参考；其设计文章不是当前安装兼容性的证明。[原始设计说明](https://wonderunit.com/shot-generator/)

代理体能展示站位、重心、手势和身体动作，但没有面部绑定时不能证明精细表情。此时表情轨道继续保留，并明确需要表情特写参考图或后续角色表演检查。

## 7. 13 阶段逐项优化与交付

保留所有编号目录；正式 JSON 和对应 Markdown 同目录。图片、预演、提示词、审核报告等放入所属阶段子目录，不创建第二套事实源。

| 阶段 | 优化重点及输入依赖 | 推荐交付物 | 用户确认 / 降级 |
|---|---|---|---|
| 01 项目设置与资料摄取 | 明确小说、剧本、分镜 JSON / 表格、参考图片与旧项目路由；保留来源片段和复制哈希 | 来源登记、输入摘要、能力初检 | 工作深度、改编边界；不可读资料请求补充，不猜测 |
| 02 输入标准化与缺口处理 | 表格 / PDF / OCR 置信度；正文与指令隔离；事实冲突逐项关联来源 | Intake Brief、缺口与冲突登记、权利记录 | 核心身份、关系、行动结果、版权及肖像必须确认 |
| 03 叙事提取与动态记忆 | 从已批准输入建立实体与状态变化；区分事实、推断、建议；记录画外状态 | Narrative Bundle、实体表、动态记忆、章节批次计划 | 多章才询问批次；记忆不能静默累积互相冲突的当前状态 |
| 04 改编方案 | 增加导演总体处理：场景目的、POV、信息揭示、节奏、视觉母题 | Adaptation Plan、Director Treatment | 关键导演路线 / 核心改编由用户选择；低风险衔接可自动提案 |
| 05 剧本创作与增强 | 台词、反应、动作目标、策略转折与可观察节拍绑定 | 剧本、增强剧本、表演节拍、对白时长估计 | 台词语义及剧情不被时长压缩静默改变；可做仅供预演的临时配音 |
| 06 故事审核与生成分段 | 先按戏剧节拍确定镜头，再组织 GenerationSegment；不机械等分动作 | 故事审核、节拍—镜头映射、分段计划 | 保留 1—12 秒 Shot 约束；10/15/20 秒是制作分段，不自动变成单镜或单请求 |
| 07 美术资产 | 角色身份、服装版本、场景结构、道具尺寸分层；参考图与几何用途分离 | Visual Bible、资产登记、角色 / 场景 / 道具图、几何代理说明 | 风格、画幅、图像执行、权限与费用；美术审核必须人工批准 |
| 08 站位与空间 | 根据剧本及资产建立可构建场景、人物路径、固定物、相机可用区域及互动约束 | SceneSpace、Blocking Plan、场景工程、俯视图、空间检查 | 用户选择 2D / 2.5D / 经验证三维并锁定空间；缺能力明确降级 |
| 09 故事板 | 从场景与节拍生成角色 / 相机 / 声音轨道；统一逐时刻求值；渲染而非只描述 | ShotTimeline、图片故事板、预演、导演轨道、连续性审核 | 深度与派生视图选择；图片不可用不能静默改文字；故事板始终人工审核 |
| 10 分镜级视频提示词 | 真正解引用风格、资产、故事板图片及空间 / 时间事实；编译完整记录与紧凑提示词 | Canonical PromptPackage、逐镜提示词、参考图槽位表、字段覆盖与降级表 | 参考上限最多 5 个上传槽位不等于逻辑资产最多 5 个；关键内容不可表达则确认换路线 |
| 11 平台适配与媒体执行 | 实际能力探测；区分本地渲染、控制视频、图片参考、实时流；保存每个 take | 实际请求与响应、作业索引、候选媒体、画面对照报告 | 平台、执行方式、上传、账号、费用；实时模式单独授权 |

| 13 最终质检与交付 | 校验失败阻断正式成功；技术与创作审核分开；检查最新修订及全部媒体 | 分层 QA、Delivery Index、交付 ZIP、封面、发布文案与检查表 | 不自动发布；可交付范围必须明确是提示词、预演、部分媒体还是已审核成片 |

## 8. 编译、生成与剪辑的专项修复

### 8.1 从“事实哈希一致”提升到“事实真实传递”

事实哈希用于证明引用的源版本，不证明文字覆盖了该事实。建议为每条必需事实登记：来源位置、重要性、目标文本字段 / 控制输入、是否支持、是否实际提交及审核状态。

- 静帧编译器只消费某一时刻的求值快照。
- 视频编译器消费整段有序轨道，区分同时与先后。
- 平台适配器不能把不可表达的轨迹悄悄删掉；关键事实丢失必须回到选择门。
- `required_asset_ids` 保留全部逻辑依赖；`selected_reference_ids` 记录实际上传的最多 5 个版本化引用，允许引用已批准故事板图片。
- 若平台会扩写提示词，保存用户提示词和实际扩写结果；不可获取的内容写为未知，不能假定与 Canonical 等价。
- 有限执行提示词优先保留身份、关键行动与结果、空间接触和时序；风格修辞可以压缩，剧情事实不能“摘要掉”。

MiniMax 的官方写法可作为其中一个平台词汇表，而不是所有平台的共同接口。[H3 官方提示词文本](https://raw.githubusercontent.com/MiniMax-AI/MiniMax-H3/main/skills/h3-prompt-writing/references/base-en.txt)

### 8.2 实际媒体作业与能力证明

新增提供方时，最小实现探测、提交、查询 / 获取结果和取消；本地三维执行器另外实现构建、渲染和回读。两者不要用环境变量假装已实现。

能力快照至少包含：具体提供方 / 模型、接口版本、输入模态、支持时长 / 分辨率 / 参考槽位、证据来源、核验时间、执行测试结果及权限状态。能力过期或合同改变影响当前任务时重新确认，不能靠历史测试永久放行。

每个媒体作业记录请求参数、提示词 / 参考文件哈希、外部作业 ID、输出文件、费用边界、失败证据和候选编号。网络失败重试与创意返修分开计数；先查询现有作业再考虑重新提交，防止重复收费。测试 fixture 始终标为 fixture。

### 8.3 Edit Plan 必须成为可执行计划

- 区分原始媒体时码、镜头本地时码和成片时间；统一帧边界及转场重叠语义。
- 严格按 Edit Plan 的顺序与入出点渲染，不按文件名排序。
- 把配音、环境声、音效、音乐和字幕真正混合 / 合成；无对白不代表一定要有对白音轨。
- 对响度、峰值、声道、字幕安全区、对白起止及完整解码分别输出证据。
- 可导出 OTIO 方便进入外部剪辑器，但它是从 Canonical Edit Plan 派生的交换文件，不是渲染器，也不是新的事实源。OTIO 官方架构提供 Clip、Track、Transition、时间范围及媒体引用概念，可作为交换映射基础。[OpenTimelineIO 文档](https://opentimelineio.readthedocs.io/en/latest/tutorials/architecture.html)

## 9. 运行时、渐进披露、迁移与安全

### 9.1 上下文与依赖

- L0 保持只读路由信息；L1 加载当前场景 / 批次所需上游；L2 仅当前专家与量表；L3 仅所选执行器和平台；L4 仅当前错误所需帧、日志及诊断。
- TaskEnvelope 指纹覆盖实际使用的 Schema、工作流与编译器版本、资源哈希、输入修订及能力快照，记录“声明要加载”和“实际已加载”的差异。
- 依赖细化到场景、实体版本和镜头，不仅是阶段序号。修改一个镜头的相机，不应自动使无关场景的美术资产重做。
- 明确读取关系：故事板图片依赖空间、轨道、相机及资产；视频提示词和实际上传参考依赖这些图片；正式批准绑定被批准的精确修订。
- 区分选择偏好与版本批准：失效时可保留仍兼容的风格偏好，但旧版审核不能沿用。

### 9.2 存储与恢复

保留 Kernel 唯一提交权。采用临时工作目录、全批校验、提交日志和原子提交点，提交期间加项目写锁。JSON、Markdown、媒体索引和状态必须具有一致的提交版本；异常后能够回滚或完成提交，不能出现半批成功。

媒体采用不可变版本目录；重试或返修生成新 take，不覆盖旧图和旧视频。批量运行先复用同输入哈希的有效结果，再执行真正失效的镜头。不提前引入分布式数据库或复杂渲染农场。

### 9.3 兼容迁移

- 不修改现有 `baseline-v0.1.0` / `v0.2.0` 标签；先建立修复提交和新的绿色基线，再进入功能分支。
- Schema 版本由兼容性决定：增加可选字段可增量演进；真实三维新增必需语义应使用新版本及显式迁移，不能仅替换版本号。
- 旧版 2.5D 项目可以继续以其原有能力范围打开；升级三维需要用户选择。没有尺寸、相机或真实图片的旧产物不能自动补成“已验证”。
- 已批准剧情与兼容的美术资料保留；受新增空间语义影响的阶段 08—13 按真实依赖重新生成和批准。阶段 07 仅在资产描述 / 尺寸 / 几何发生实际变更时失效。
- 正式提供原地非破坏迁移、只读、复制新项目三种路径，并记录迁移前证据。

### 9.4 新增执行面的安全边界

以下是新增 Blender / 外部服务后的防护建议，不表示本轮已发现对应漏洞：

- 小说、网页、资源元数据中的指令均视为资料，不授予执行权限。
- 外部 `.blend` 默认禁用自动脚本执行；场景构建限于项目目录和批准资源，渲染设置时间 / 内存预算。
- MCP 或模型生成的脚本先静态限制、隔离执行；不可因“导演建议”获得任意文件访问或上传权限。
- 账号、密钥和授权令牌不写入正式 JSON、报告或 ZIP；外部请求保留可审计但脱敏的记录。
- 用户必须确认外发范围和费用上限；内容授权不能由模型猜测；依旧不自动发布。

## 10. 用户需要选择什么

只在到达对应阶段时询问。推荐项不是批准；低风险技术细节在既有授权范围内自动处理，不用把用户变成参数填写员。

| 选择门 | 用户看到的内容 | 推荐处理 |
|---|---|---|
| 创作方向 | 紧张 / 克制 / 夸张等与具体剧本相关的少量导演方案及画面差异 | 在阶段 04 提供少量有实际区别的候选，不预设某种审美 |
| 风格与画幅 | 沿用现有明确选项，加参考图说明 | 阶段 07 确认，未确认不生成正式资产 |
| 空间表达 | 2D、2.5D、已验证真实三维及各自限制 | 能力不支持的选项说明原因，不以“推荐”绕过能力门 |
| 故事板与预演 | 深度、派生视图、是否输出图片 / 动态预演 | 图片 / 三维项目应验收实际画面；无能力时明确选降级、补能力或暂停 |
| 制作路线 | 直接渲染、控制视频风格化、图片参考视频、实验实时流 | 首次验证优先离线三维预演；生成路线另行确认 |
| 美术 / 空间 / 故事板审核 | 实际图、预演、变化清单及已知缺陷 | 保留三个人工批准门，快速模式也不跳过 |
| 声音与交付 | 配音策略、语言、成片或仅执行包 | 明确未实现环节；账号、付费、资料上传单独确认 |

返修时优先提供能理解的修改意图，例如“让第二镜视线先看门再看对手”“保留走位，仅换成侧后方机位”。Agent 将其转成受限修改提案，展示影响镜头和重生成范围，再按既有批准规则执行。

不建议一次改完所有能力。下面每一步均以实际验收作为进入下一步的条件；没有预估未经测量的工期和收益。

| 里程碑 | 范围 | 必须通过的验收 | 暂不做 |
|---|---|---|---|
| M0：可靠性修复 | 最终门、返修恢复、批次事务、输入误路由、能力真假、提示词字段丢失 | 保留 31 项；固化本轮反例；失败不会得到正式成功；返修后能再到达合法交付 | 不接新模型、不改 UI |
| M1：导演契约与三维核心 | 导演意图、严格场景 / 相机 / 时间、状态求值、Blender 本地执行 | 单场景生成真实 `.blend`、相机帧及俯视图；改相机能改变画面；米制转换正确 | 不做复杂角色绑定和实时云视频 |
| M2：图片故事板与预演 | 瞬时状态驱动图片、轨道预演、画面检查、故事板到提示词引用 | 阶段 07—10 实际串联；逐镜图片 / 预演可看；修改表演能传到提示词 / 画面证据 | 不假装代理体已有电影级表情 |
| M3：一条生成路线与完整剪辑 | 经确认接一个提供方；真实作业；Edit Plan 解释、声音混合及最终 QA | 授权小样生成；文件与计划对照；非字典序剪辑正确；校验失败阻断交付 | 不同时支持所有平台 |
| M4：扩展与实验 | 镜头级缓存、候选管理、预算；可选交互 UI / MCP / 实时流 | 只重做受影响镜头；取消 / 恢复 / 费用边界验证；实时路径单独测试 | 不为未验证需求建设大平台 |

### 11.1 最小黄金场景

建议样本：一间房、两个人、一扇门、一张桌、一个可交接道具，6 个镜头，每镜 4 秒，共 24 秒。24fps 下得到 576 帧预演。人物由警惕转为确认，通过视线、停顿和道具交接推动情节。此样本是验收建议，不是本轮已生成作品。

交付必须包含：批准记录、角色 / 场景 / 道具资产、尺寸明确的场景、6 条人物和相机轨道、实际图片故事板、完整预演、逐镜提示词、来源覆盖表及 QA。

重点反例与验收：

1. **失败不交付**：破坏派生视图，最终状态不得 complete / export_ready；只允许标记失败的诊断包。
2. **事务与恢复**：第二镜无效或提交中断，不留下半批正式结果；修复后能够续跑。
3. **相机投影**：世界人物不动、只改相机，屏幕投影与实际图像相应改变；标注预期值及容差。
4. **坐标与时间**：标准化 / 米制转换结果一致；关键帧之间正确插值；镜头、片段和成片时间无累计漂移。
5. **互动与画外**：道具同一时间仅一个合法持有者；交接时手与道具关系满足代理精度；出画人物仍保留世界轨迹。
6. **遮挡与构图**：关键动作 / 道具不被意外遮挡；测试故意穿墙相机、越界路径和空镜主体，必须被报告。
7. **表演传递**：修改视线、外显表情或动作触发点，覆盖表和提示词必须变化；有对应绑定时渲染也必须体现。
8. **交接语义**：连续动作正确接续；经过批准的跳时 / 换场可以改变状态；不能用空泛 transition 字段跳过检查。
9. **图片能力边界**：真实渲染 PNG、AI 图片、fixture 和提示词降级标签不同；没有图片时不能通过图片交付验收。
10. **引用与缓存**：改一镜相机，仅重建真正受影响的快照、图片、提示词及下游；无关资产哈希不变。
11. **编辑与声音**：使用故意不按 ID 排序的 Edit Plan，验证剪辑顺序、转场、配音和字幕确实进入成片。
12. **能力与授权**：不存在的提供方不能激活真实三维；外部生成缺少授权不提交；中断恢复不得重复收费。

技术正确通过后，再用带完整人物模型的剧情样本评审表演与审美，不能从盒子和圆柱体预演直接宣称“出色的导演效果”。
