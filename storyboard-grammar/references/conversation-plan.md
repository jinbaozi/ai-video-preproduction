### 对你的 Skill，怎样使用这些案例？

**人名用于检索案例，规则用于执行。**

不建议这样设计：

```text
选择大师：科恩兄弟
生成：高级、冷峻、有电影感的分镜。
```

我建议转换为：

```text
叙事目标：让观众在角色开口前察觉关系变化。
执行规则：
  建立双方位置与视线关系。
  将行动镜头与反应镜头分别分配。
  在关键信息出现前保留必要遮挡。
  每次切镜说明信息变化或反应价值。
验收：
  去掉台词后，观众仍能判断谁占主动、谁在回避。
```

这样得到的是**可以复用、可以解释、可以检查的分镜语法**，而不是人名标签。

## 四、在你的现有体系里，分镜师应当放在哪里？

你的美术 Skill 已明确要求继承宿主的 canon、角色／场景／道具 ID、资产版本和审批，不创建第二套事实源或全局状态机。这一边界应当延续到分镜层。fileciteturn1file1L76-L80

我建议采用以下结构：

```text
原文 / 已批准故事
        │
        ├── director-grammar
        │     叙事目的、视点、导演选择
        │
        ├── production-design-grammar
        │     视觉世界、场景、服化道、资产约束
        │
        ▼
storyboard-grammar
  来源与范围
    → 节拍覆盖
    → 风格语法
    → 空间与人物调度
    → 镜头设计
    → 动作 / 表情 / 声音
    → 画格与转场合同
    → StoryboardIR + 制作合同 + QA
        │
        ▼ 版本协商
宿主合并 AVIR / Context-IR
        │
        ▼
video-prompt-compiler
  原生提示词、参数、参考绑定、执行任务、损失报告
        │
        ▼
模型生成 / 可选 Hypit / 剪辑
        │
        ▼
真实媒体与成片验收
```

### 最重要的职责界线

**导演决定表达意图；美术定义视觉世界；分镜把二者落实为可见、可拍、可剪的镜头方案；编译器将方案映射到具体平台。**

分镜师可以发现问题并提出改变机位、动作或镜头结构的建议，但不能在后台改写导演决定、台词或角色设定。

四个 Skill 应当独立安装、升级和测试，通过版本化文件或消息协作，不依赖相邻目录中的实现代码。

## 五、必须分开的七种对象

这是我认为整个方案中最重要的建模决策之一。

| 对象 | 含义 | 常见误用 |
|---|---|---|
| **Scene：场景** | 时间与空间环境 | 把每张图当成一个新场景 |
| **Beat：叙事节拍** | 一次行动、反应或信息变化 | 用固定秒数代替剧情拆解 |
| **Shot：镜头** | 连续摄影表达单元 | 默认一个生成任务等于一个镜头 |
| **Panel：画格** | 镜头中的一个可见节点 | 默认一张分镜图等于一镜 |
| **GenerationJob：生成任务** | 一次模型执行 | 把模型时长上限当成叙事规则 |
| **Take：候选素材** | 实际生成或拍摄出的版本 | 把提示词计划当成已完成素材 |
| **EditSegment：剪辑片段** | 被采用素材中的一个时间区间 | 忽略实际剪点与声画衔接 |

例如：

> 一个连续跟拍镜头，包含“伸手—接触—松手—转身”四张画格，仍然是一个镜头。  
> 一次原生多镜头生成任务，可能包含三个镜头。  
> 一页九宫格，只是一种审阅排版。

因此，**画格数量不应该由模型附件上限决定，镜头时长也不应该由某一代模型的默认值决定。**

## 六、怎样实现风格自适应，而不是堆积“大师风格”？

### 1. 将风格拆成三条独立轴

```text
视觉媒介 × 叙事语法 × 交付格式
```

例如：

```text
水墨与三维混合 × 动作空间清晰 × 9:16 竖屏
实拍质感       × 悬疑信息揭示 × 16:9 横屏
角色动画       × 喜剧反应节奏 × 短篇叙事
```

“仙侠”不应自动意味着环绕、慢动作和浅景深；“竖屏”也不意味着每镜只拍一张脸。

### 2. 使用功能型语法卡

参考包中已有十种：

| 语法卡 | 主要控制目标 |
|---|---|
| 透明叙事与人物关系 | 观众能理解谁在行动、谁在反应 |
| 悬疑与信息揭示 | 控制何时看见什么，而不是只添加暗光 |
| 动作与空间关系 | 路线、接触、危险、结果可读 |
| 喜剧与反应节奏 | 建立预期、停顿、反应和结果 |
| 观察式与长镜头 | 让变化发生在镜内，而不是靠切镜补救 |
| 角色动画与姿态表演 | 姿态、情绪节拍和动作轮廓 |
| 武侠仙侠与纵深调度 | 方位、高度、距离与场景层次 |
| 产品演示与商业展示 | 产品信息、操作关系和展示证据 |
| 竖屏短剧与人物互动 | 人物组合、脸手道具与安全区 |
| 主观记忆与联想蒙太奇 | 现实关系与主观关联的边界 |

每张卡都应包含适用条件、目标、执行规则、禁止项和验收条件，而不只有一组形容词。

### 3. 路由过程应当可解释

建议的生产级流程是：

```text
检查硬约束
  → 识别场景目的、视点、动作与对白负荷
  → 选择主语法
  → 添加不冲突的局部修饰
  → 输出选择理由
  → 检查与导演 / 美术约束的冲突
  → 通过评测更新规则
```

**当前参考包的 `route` 是标签匹配建议，不是已训练的创作质量预测器。** 它会显示匹配词与计数，由宿主 Agent 或人完成选择；编译时只读取选中的语法卡。语义路由与效果优化应在端到端生成评测之后扩展。

## 七、专业分镜的核心，不是镜头术语，而是制作合同

下面这些工作规范是我为你的系统提出的设计要求。

### 1. 镜头必须有叙事目的

每镜都应回答：

> 观众跟谁观察？  
> 必须获得什么信息？  
> 谁在行动，谁承担反应？  
> 为什么移动摄影机？  
> 为什么在这里切？

只写“中景、35mm、环绕、电影感”不能回答这些问题。

### 2. 世界空间与画面位置分开

需要记录人物起止位置、朝向、视线对象、接触点、遮挡和行动轴。

“在左边”必须说明是世界左侧、人物自身左侧，还是当前画面的左侧。相机反打后，同一盏世界灯不应该仍被强制写成“画面左侧”。

**坐标也是设计意图，不等于模型原生支持三维控制。** 需要硬几何约束的镜头，应使用预演、实际参考或其他受控执行渠道，并检查生成结果。

### 3. 心理活动转成可见表演

不建议：

```text
B非常紧张，内心充满怀疑。
```

建议在导演许可范围内落实为：

```text
B的视线落在信封上。
指尖停在桌沿，没有接触信封。
B抬眼看向A，问出原台词。
A点头后，B才伸出右手。
```

表情还要匹配景别：不能让大全景中不可辨认的眼睑变化承担关键剧情。

### 4. 动作有起因、接触与结果

例如递交信封：

```text
A持有
  → 信封接触桌面
  → A松手
  → B右手接触
  → B拿起
  → B持有
```

跨镜头检查的是这条事件链，而不是一句“保持动作连贯”。

### 5. 声音有独立归属

对白、旁白、画外音、环境声、动作音和音乐分别记录。台词逐字保真、说话者正确、口型正确和混音可听，是不同的验收项。

文本检查通过，不能升级成声音检查通过。

### 6. 每条要求形成合同

  - SRC_SCRIPT

  type: equality

这里的结构检查只证明 `state_end` 符合合同。成片中是否真的由 B 右手持有，还需要媒体证据。

## 九、Hypit 应该怎样接入？

我建议把 Hypit 放在**执行与组装侧**，而不是让它成为故事、角色或分镜的事实源。

Hypit 的公开材料将视频创作语言、模型／Provider、Runtime 和测试边界分开；其 README 还说明了将字幕、画面等锚定到词语，以及不调用生成模型也能编译部分确定性视频内容的思路。这些适合借鉴到你的执行层。citeturn910051view0 

建议的交接关系是：

```text
StoryboardIR 的镜头 / 动作 / 声音事件
      ↓
video-prompt-compiler 的生成任务与后期任务
      ↓
经版本验证的 Hypit 源文件与执行配置
      ↓
实际素材、渲染、剪辑与验收
```

模型生成与字幕、版式、合成等确定性工作分别安排。具体源语言和命令以所锁定的 Hypit 版本为准。

本包**没有生成可执行 SVML，也没有运行 Hypit**。此外，Hypit 的许可证是带附加条件的 Apache 2.0 变体，对多租户服务、商业再分发和标识使用有额外规定，不能当成普通 Apache 2.0 使用。

## 最终建议

**不要先扩充到几十种大师风格，也不要先接入所有视频平台。**

优先把这条路径跑通：

> **原文 → 导演／美术约束 → 三镜头分镜 → 持物与空间合同 → 现有 AVIR → 一个真实模型入口 → 成片逐项验收。**

通过之后，再扩展语义风格路由、复杂动作、动态轴线、三维预演、音频时间对齐和多平台后端。

这样构建的分镜师 Skill，核心价值不是“会写更多摄影词”，而是：**每个镜头知道自己要表达什么，每个动作知道前后发生了什么，每条制作要求知道由谁执行、拿什么验收。**
